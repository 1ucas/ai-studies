AI Study Guide — Cheat Sheet

Everything you need on model economics, agent plumbing, and the SDD / MCP / RAG vocabulary that's essential to master as a software engineer working with AI. Numbers are August 2026 list prices — they will move, the relationships won't.

01 Main Concepts — the vocabulary first

Anchor terms you'll see thrown around in the rest of the guide and in the study. Each is 2–4 sentences — enough to use the word fluently without faking it.

1.1 Token

The unit an LLM reads and writes. Roughly a chunk of 3–4 characters in English (a short word, or a piece of a long word). "Hello, world!" is about 4 tokens. Models are priced per token, have context windows measured in tokens, and generate one token at a time. The tokenizer is the (deterministic) algorithm that splits text into tokens — and different tokenizers can change your bill even when the visible text looks identical.

1.2 Transformer

The neural-network architecture that powers every modern LLM (GPT, Claude, Gemini, Llama, DeepSeek, Kimi — all transformers). Introduced in the 2017 paper "Attention Is All You Need." Replaced the older RNN/LSTM approach. The transformer's superpower is that it processes all tokens in a sequence in parallel (instead of one-at-a-time like RNNs), which is what made training on internet-scale data feasible.

A transformer is built out of stacked "blocks." Each block does two things: attention (look at relevant other tokens) and a feed-forward layer (process each token independently). Stack ~30–100 of those blocks, train on trillions of tokens, and you have an LLM.

1.3 Attention

The mechanism inside a transformer that lets each token "look at" other tokens in the sequence and weight how much each one matters. When the model is generating the next word after "The cat sat on the …", attention is what lets it look back at "cat" and "sat" — and weight them more heavily than filler words — when deciding the next token.

Concretely: every token produces three vectors — Query (Q), Key (K), Value (V). The Query of the current token is compared (dot product) against the Keys of all other tokens to produce attention scores. Those scores weight the Values, which get summed → the token's new representation. "Self-attention" means tokens attend to other tokens in the same sequence.

Attention is also the most expensive part of a transformer. Naive attention is O(n²) in the sequence length — double the context, 4× the cost. Variants like Flash Attention, sliding-window attention (Mistral), Multi-Query Attention (PaLM), Grouped-Query Attention (Llama 3), and linear attention (Mamba/RWKV hybrids) all try to reduce that cost. Modern long-context models (Gemini 1M+) almost certainly use a mix of these.

1.4 Context window

The maximum number of tokens the model can see in a single request — input + output combined (or sometimes counted separately, varies by provider). When you hear "Gemini has a 1M context window," it means the model can hold ~1 million tokens of input. Bigger window → more documents/code/conversation history you can shove in without RAG.

1.5 Chain-of-Thought (CoT)

The model's intermediate "thinking" — written out step-by-step before producing a final answer. Introduced as a prompting trick in 2022 ("Let's think step by step…") and now baked into reasoning models as a built-in behavior. Three flavors to know:

  • Prompted CoT — you ask the model to think step by step. Works on any model.
  • Visible reasoning — the model emits step-by-step reasoning into the response (you and the user see it).
  • Hidden / provider-owned "thinking" — used by OpenAI reasoning, Claude extended/adaptive thinking, Gemini Thinking, and DeepSeek V4 Pro thinking mode. The model spends extra generated tokens on internal reasoning; providers may hide it, summarize it, encrypt/sign it, or expose special thinking blocks. You pay for those thinking tokens — that is why reasoning models can cost 5–30× more in output.

Why it works: writing intermediate steps gives the model more "compute" to reach the right answer (it allocates more forward passes to harder questions). Why it costs: you are literally paying for thousands of extra output tokens you never see.

1.6 Mixture of Experts (MoE)

An architectural trick to make models bigger without proportionally more compute per token. Instead of one giant feed-forward block per layer, you have N "expert" blocks plus a small router network that picks 1–2 experts to actually run for each token. The model has a huge total parameter count, but only a small active count per forward pass.

Example: Kimi K3 has 2.8T total params but routes each token through just 16 of its 896 experts — a classic MoE at extreme scale. DeepSeek V4 Pro attacks the same problem (1.6T total / 49B active) but uses DSA (DeepSeek Sparse Attention) rather than traditional MoE. You get the knowledge breadth of a giant model at the inference cost of a much smaller one. Trade-off: all expert weights must reside in VRAM at all times, even those not selected for a given token — so weight residency is higher than a dense model of equivalent compute cost. The flip side is that compute per token is lower (only the active experts run matrix multiplications). Routing can also be uneven: popular experts get overloaded while others sit in VRAM without contributing.

Most open-weight models are MoE in 2026 — from cheap DeepSeek to the 2.8T Kimi K3. Closed flagship models (GPT-5.x, Claude 5 / 4.x, Gemini 3.x) are widely believed to be MoE but the labs do not confirm architecture details.

1.7 Classifier

A model (often small) whose job is to assign one of a fixed set of labels to an input. "Is this email spam or not-spam?" "Is this user question about billing, technical, or account?" Output is a category (or a probability over categories), not free text.

In LLM systems classifiers do the cheap upstream work: intent detection, routing, safety filtering, relevance scoring. They can be (a) a fine-tuned small model like DistilBERT/Llama-3.1-8B, (b) a frozen LLM prompted to output a single label, or (c) a classical ML model (logistic regression on embeddings). Big LLMs are overkill — a fine-tuned small classifier is faster, cheaper, and usually more accurate on a fixed taxonomy.

1.8 Routing (in LLM systems)

The decision of which model (or which tool, or which downstream component) should handle a given request. "Routing" appears at multiple layers:

  • Model routing — pick which LLM (Haiku vs Sonnet vs Opus). The §03 topic.
  • Tool routing — given a request, pick which tool/function the agent should call.
  • Skill routing — pick which sub-agent or specialized prompt handles this.
  • Expert routing — inside an MoE model, the router network picks which experts fire for a given token (different layer of abstraction — same word).

A "router" is usually a classifier (see 1.7) — that's why the two concepts are joined at the hip.

1.9 Model lab vs Provider vs Inference platform

Three things that often get conflated:

  • Model lab — who trained and owns the model. Anthropic, OpenAI, Google DeepMind, xAI, NVIDIA, Meta, DeepSeek, Moonshot, Z.ai, Mistral, Alibaba (Qwen).
  • First-party provider — the lab serving its own model via API. api.anthropic.com, api.openai.com, ai.google.dev.
  • Third-party inference platform — a company that hosts other labs' models (usually open-weight) on their infrastructure. Together AI, Fireworks, DeepInfra, Groq, Replicate, OpenRouter.
  • Cloud-vendor reseller — your existing cloud account, with frontier models bolted on. AWS Bedrock, Google Vertex AI, Azure OpenAI Service.

“Different provider models per sub-task” in the routing pattern (§03) means: this step uses an Anthropic-hosted Sonnet; the next uses a Together-hosted Kimi K3; the embedding step uses Voyage. Different vendors, one workflow.

  • Trade-off: new model versions usually land on the lab's first-party API days-to-weeks before Bedrock/Vertex. And pricing on these platforms is sometimes ~5% higher than the direct API.
Key insight: "For enterprise AI, the model is rarely the limiting factor — procurement, data residency, and IAM are. Bedrock and Vertex exist because they let you adopt frontier models without re-doing your compliance posture."

How to read this table

  • MoE → cheap inference, big memory. An MoE activates only a fraction of the weights per token — Kimi K3 has 2.8T parameters but routes each token through just 16 of 896 experts, so per-token compute is that of a much smaller model. Trade-off: you need RAM for all 2.8T at once. DeepSeek V4 attacks a different layer: its DSA (DeepSeek Sparse Attention) makes attention itself sparse, making V4 Pro (1.6T/49B) cheaper to serve than its parameter count suggests.
  • Long context = attention variant. When you see "1M context" (Gemini, GPT-5.6, Claude 5, Kimi K3), the model is not using naive quadratic attention at full cost — it's using cheaper attention/cache strategies. The labs rarely publish exactly what.
  • Reasoning mode is now often a request parameter, not a separate model. Claude has adaptive thinking (always on in Fable 5), GPT-5.6 has reasoning effort (up to "Max"), Gemini 3.x has thinking budgets, and DeepSeek V4 exposes thinking/non-thinking modes.
  • Tool-use quality varies more than raw IQ. The benchmark gap between Sonnet 5 and Kimi K3 on raw reasoning is small. The gap on "follows a 12-step tool sequence without going off the rails" is narrower than it used to be, but still where Anthropic leads.
  • "GQA" / "MLA" — Grouped-Query Attention (used by Llama, most modern transformers — fewer K/V heads than Q heads → cheaper) and Multi-head Latent Attention (DeepSeek's invention — compresses KV cache, lets them serve 128K context cheaply).

Reasoning vs non-reasoning — when each is worth it

Reasoning models/modes (Claude Fable 5 and Opus 5 adaptive thinking, GPT-5.6 Sol Max, GPT-5.5 Pro, DeepSeek V4 Pro thinking mode) burn many extra output tokens on provider-owned internal thinking. Use them when:

  • The task has a verifiable correct answer — math, code that must pass tests, logical puzzles.
  • The task is multi-step planning where a wrong early step poisons the rest.
  • You can afford 5–30× more output tokens and 2–10× more latency.

Do not use them for chat, summarization, classification, or anywhere the answer is "open-ended" — you pay for thinking you do not need.

2.2 Open vs closed source

The other axis that defines a model is whether its weights are public. Closed frontier labs (Anthropic, OpenAI, Google, xAI) rent you an API; open-weight labs (DeepSeek, Moonshot, Z.ai, Alibaba, NVIDIA) publish weights you can run yourself. In 2026 the capability gap between them has nearly closed — these are the open contenders worth knowing:

  • Kimi K3 (Moonshot AI) — released Jul 16, 2026; full weights publishing by late July. 2.8T params (896-expert MoE, 16 active/token) — the largest open-weight model ever released. Multimodal, reasoning-native, 1M ctx. Top-3 overall on GDPval-AA (behind only Fable 5 Max and GPT-5.6 Sol Max, ahead of Opus 4.8, the then-current Opus) and #1 on the WebDev arena. The catch: it charges closed-frontier prices ($3/$15) — which today is more expensive than Claude Sonnet 5 ($2/$10).
  • DeepSeek V4 — the price/performance reference. V4-Pro-0813 left preview and went GA on Aug 13, 2026, aimed squarely at agentic work (Terminal Bench 2.1 87.9, DeepSWE 62.7, NL2Repo 61.5), with low/high/max effort levels and native Responses API support. V4 Flash (build 0731) for general work ($0.22/$0.66 off-peak), V4 Pro for top quality on a budget ($0.66/$1.98 off-peak; 49B active / 1.6T total, DSA architecture). 1M context and 384K output across the line, plus an experimental multimodal v4-flash-vision-exp. The new rates took effect Aug 16, 2026 and still carry 2× peak windows.
  • GLM 5.3 (Z.ai / Tsinghua) — the 5.2 successor at the same price ($1.40/$4.40), 1M ctx / 128K output. Flagship agentic and offensive-security model: DeepSWE v1.1 66.9, Terminal Bench 3.0 28.3, CyberGym 84.5%, ExploitBench 54.4%. Built for long-horizon autonomous work — multi-hour sessions. Available on HuggingFace, vLLM, SGLang, and api.z.ai.
  • Qwen 3.8 (Alibaba) — open-weight family. Strong multilingual/CJK, competitive coding. The Qwen3.8-Max flagship (GA Aug 3, 2026; $1.65/$4.95 on Model Studio's price list, 1M ctx / 131K output) picked up a weights release in mid-August — but the open weights are text-only and drop the native 1M context; the hosted API remains the full multimodal version. Don't confuse the two.
  • Nemotron 3 (NVIDIA) — the US open bet. Three sizes: Nano (30B-A3B hybrid Mamba2-Transformer MoE, 1M ctx, Dec 2025), Super (~100B, Mar 2026), and Ultra (~500B, Jun 2026 — leading US open-weight intelligence, ~5× faster inference). Extremely cheap to serve — Super runs $0.085/$0.40 per 1M on reference hosts (OpenRouter, DeepInfra) and is free on some providers — ideal for high-volume agent fleets.
  • Llama / Mistral families — broad ecosystem, fine-tunable, on every inference provider.
Mental model: The open-vs-closed price boundary is collapsing from both ends. From above, Kimi K3 now charges closed-frontier prices ($3/$15) and delivers top-3 performance — and since Sonnet 5 locked in $2/$10, the top open-weight model is more expensive than the closed mid tier. From below, DeepSeek V4 and GLM 5.3 remain 5–30× cheaper than closed flagships. The closed premium still buys: tool-use reliability, long-horizon coherence, multimodal depth, and ecosystem (tools, caches, hosted retrieval). For batch extraction or classification, the cheap open/flash tier still wins by an order of magnitude.

3.3 Routing patterns you should be able to name

  • Cascade / triage routing — cheap model answers; if confidence low or a "hard" classifier flags it, escalate to the expensive model. Common shape: Haiku 4.5 → Sonnet 5 → Opus 5. Cuts cost 60–80% with minimal quality loss.
  • Task-typed routing — a classifier (sometimes an LLM, sometimes a fine-tuned small model) tags the request (code, chat, math, vision) and dispatches.
  • Speculative / draft-then-verify — cheap model drafts, expensive model verifies / edits. Used in agentic coding (e.g. Haiku proposes, Sonnet reviews).
  • Mixture-of-Experts at the orchestration layer — same name as in model architectures, but here it means routing to different provider models per sub-task in a workflow.
  • Provider failover — primary on Anthropic, fallback to Bedrock-Anthropic or to OpenAI on outage. Tools: OpenRouter, Portkey, LiteLLM.

3.4 Decision flow (the "out loud" version)

  1. Is the data sensitive / regulated? Yes → open-weight on your infra. Stop.
  2. Does the task fit in < 8K tokens and have a small fixed schema? Yes → Haiku 4.5 / GPT-5.6 Luna / DeepSeek V4 Flash.
  3. Does it need to reason multi-step over code or math? Yes → Sonnet 5 → Opus 5 / Fable 5 / GPT-5.6 Sol Max / DeepSeek V4 Pro (thinking mode).
  4. Is it a long document (> 200K tokens)? Yes → Gemini 3.7 Flash / Claude Opus 5.
  5. Is it multimodal? Yes → Gemini 3.7 Flash first.
  6. Default agentic coding / tool use → Sonnet 5.
  7. Then ask: can I cache 80% of this prompt? If yes, the choice gets cheaper by 10×.
Common pitfall: Do not recommend "the smartest model" reflexively. In production, 80% of tokens go to routine work — and using Opus for routing is a costly mistake at scale. The right answer is almost always "I would route — here is the cascade."
Killer line: "There is no best model. There is a portfolio. Frontier for the hard 5%, Sonnet-tier for the agentic 15%, Haiku/Flash for the 80% that is routing, classification and extraction. Cost-aware routing is how you make AI products profitable in 2026."

3.5 Self-hosting — the personal & enterprise reality

"Just run it yourself" sounds cheaper than it is. Two very different situations:

  • Personal (a workstation). A high-end MacBook Pro or Mac Studio with 100+ GB of unified memory can genuinely run some open-weight models locally — a quantized DeepSeek V4 Flash, GLM 5.3, Qwen 3.8, or Nemotron 3 Nano — via runtimes like Ollama, LM Studio, or llama.cpp. Great for privacy, tinkering, and offline work. But you are running quantized, mid-tier weights at a few tokens/second — not the frontier.
  • Enterprise (a GPU fleet). Serving full-weight frontier-class open models (Kimi K3 at 2.8T params, DeepSeek V4 Pro at 1.6T) at production throughput needs a cluster of H100/H200-class GPUs — hundreds of GB of VRAM, vLLM or SGLang, and an ops team. The hardware and power bill for that is still out of reach for most small and mid-size companies.

The honest 2026 takeaway: self-hosting full-weight AA-tier models is still too expensive for common use — even for small companies. When the data cannot leave your perimeter, the realistic middle ground is a managed inference provider (Together, Fireworks, DeepInfra, Groq) that hosts open weights on their hardware, or a cloud gateway (Bedrock / Vertex) with VPC isolation. You get open-weight economics and data control without owning the GPUs.

Why this matters: Internal tools at a company often can't ship customer data to OpenAI/Anthropic. Open-weight + a managed inference provider (Together, Fireworks, DeepInfra, Groq) or self-hosted vLLM is the realistic answer. Know that vocabulary.

4.4 Context flow: how input + output feed the next call

Every multi-turn app is either stateful or stateless:

  • Stateful: provider stores prior turns. You pass a conversation/response id such as OpenAI's previous_response_id. Easier, but you depend on provider-side state.
  • Stateless: your app stores the conversation. On each request you send the relevant prior user messages, assistant outputs, tool calls, tool results, and retrieved context.

The safe stateless loop is: user input → model output items → tool results → model final answer → next user input. Do not summarize or mutate provider-owned reasoning/signature blocks in the middle of a tool loop; several APIs require those blocks exactly as returned.

Context rule: The assistant output is not just display text. It may be required protocol state. If you throw away tool-call ids, reasoning items, thought signatures, or content-block ordering, the next API call can fail or reason worse.

You usually do not send raw vectors to the generation model. Vectors live in the retrieval layer. The model receives the retrieved text, metadata, and citations.

  2. Query: embed the user's question using the same embedding model family.
  3. Retrieve: vector search + BM25/hybrid + rerank top results.
  4. Generate: send the top snippets as normal input text: source title, URL/file id, chunk text, and citation id.

Hosted file-search pattern

Some providers manage the vector store for you. In OpenAI's Responses API, for example, you upload files into a vector store, then pass a hosted tool config such as { type: "file_search", vector_store_ids: ["vs_123"] }. Common pitfall: RAG is not "send embeddings to the LLM." It is "use embeddings to choose text, then send the chosen text to the LLM." The only exception is a provider-managed retrieval tool, where you send a vector-store id and let the provider handle retrieval.

4.8 What to log from every model call

  • Request id from provider headers/response metadata for support and incident debugging.
  • Model version, prompt/template version, tool schema version, and retrieval index version.
  • Usage: input, cached input, visible output, reasoning/thinking tokens, total tokens, latency.
  • Tool trace: tool name, args hash, auth principal, result status, retry count, duration.
  • Retrieval trace: query, embedding model, top-K ids, reranker scores, source ids actually cited.
Production rule: "The model API is an event loop with billing. Treat every response item as typed data, preserve provider-owned reasoning/signature items, and make tools/retrieval observable enough to replay."

05 Harness — the runtime around the model

A model is a stateless request/response endpoint: prompt in, tokens out. A harness is the software loop wrapped around it that makes that endpoint behave like an agent — assembling context, calling the model, parsing the response, executing any tool calls, and deciding when to stop. Claude Code, Cursor, Codex, Cline, Aider — these are all harnesses. The model is the engine; the harness is the chassis, transmission, and steering.

Mental model: "model" + "harness" + "system prompt + tools + permissions" = an agent. Same harness, different system prompt and toolset, different agent. Same model, different harness, completely different product.

The agent loop

What a harness actually owns

  • Context assembly — pick the system prompt, format tool schemas, prune old messages, inject memory and RAG snippets, attach files. The hard part of agent quality lives here.
  • Model call mechanics — streaming, retries, fallbacks (route to a cheaper model first, escalate on failure), prompt caching, preserving provider-required fields (thinking blocks, previous_response_id).
  • Output parsing — separate user-visible text from tool calls from internal thinking; handle partial streams; surface stop reasons.
  • Tool execution — validate arguments, check permissions, sandbox or timeout, capture stdout/stderr, summarize large results before feeding them back.
  • Loop control — when to continue, when to stop, iteration caps, recovery from bad tool calls.
  • Side effects & observability — write files, post to GitHub, emit traces, log token usage, redact secrets.
  • UX surface — slash commands, hooks, subagents, approval prompts, status lines.

Build vs extend vs buy

  • Extend an existing harness — first instinct for coding agents. Claude Code, Cursor, and Codex are extensible via MCP servers, subagents, hooks, slash commands, and skills. Rebuilding the loop yourself just to add a tool is wasted work.
  • Build with an SDK — when you need an agent embedded inside your own product (a support bot, an internal ops agent, a CI step). Claude Agent SDK or OpenAI Agents SDK give you the loop, tool execution, and streaming for free; you bring the system prompt and tools.
  • Build from scratch on raw API calls — only when you need very tight control over context, custom turn structure, or a non-standard tool protocol. Most teams who try this end up reinventing a worse SDK.
  • Use a graph framework (LangGraph, LlamaIndex Workflows) when the agent is actually a fixed DAG of steps, not a free-form loop. See §11.

Common harness pitfalls

  • Dropping thinking blocks on continuations. Anthropic requires the last assistant message's thinking blocks be passed back on tool-use turns; strip them and you get errors or degraded reasoning.
  • Returning raw tool output. A 350KB JSON blob in tool_result dilutes attention, evicts cached prefixes, and crosses long-context pricing tiers. Summarize before you echo. See §15.
  • Unbounded loops. "Keep going until the model says stop" without an iteration cap is how agents burn $50 in tokens overnight.
  • No permission boundary. If the model can write files, hit prod APIs, or push to git without a confirmation gate, the blast radius of a single hallucination is the whole repo.
  • Stateless tool execution. Each tool call needs an idempotency story — retries on transient failures, no double-charging, no double-posting.
  • Conversation history as the only memory. Pure scrollback hits the context ceiling fast. Add summarization, episodic memory, or external state for anything multi-session. See §06.

2026 nuance

Harnesses are converging on a small set of conventions: MCP for tools, subagents for parallelism and context isolation, hooks for deterministic policy enforcement, skills for reusable procedural knowledge. Choosing a harness in 2026 is mostly choosing a UX (terminal vs IDE vs web vs autonomous) and an extension model — the underlying loop is no longer the differentiator.

06 Memory types in AI agents

Drawn from cognitive science. Four types — know them all.

Short-term / Working / In-context

Everything inside the current context window. Like RAM — gone when the session ends. Cheap, fast, limited.

Examples: current conversation, this turn's tool outputs, scratchpad.

Episodic (long-term)

Specific past experiences with temporal context. "Last Tuesday Lucas asked me to refactor X."

Storage: vector DB for semantic search + event log for ground truth.

Semantic (long-term)

Factual knowledge, decoupled from when you learned it. "Lucas's preferred language is C#."

Storage: structured DB for facts + vector DB for concept embeddings.

Procedural (long-term)

"How to do things." Workflows, tool sequences, learned policies. Often encoded in the system prompt / agent definition itself.

Storage: system prompts, fine-tuned weights, skill files.

Architecture in 2026

  • Vector memory = retrieves semantically similar items.
  • Graph memory = retrieves relationally connected items. Production-grade by early 2026 (was experimental in 2024).
  • Memory compression: the "fundamental cognitive step" of moving short-term → long-term. Filter signal from conversational noise.
  • Frameworks: mem0, Letta (formerly MemGPT), Zep, Redis-based stores.

07 Prompt Engineering — the first era

The original discipline: writing the single-turn instruction so the model's next response matches intent. When models were weaker and interactions were one-shot, the words you chose were the whole game. Prompt, context, and loop don't compete — they stack: every context system still contains a prompt, and every loop still fires prompts. What changed is where the differentiator lives, as models and agents matured.

8.1 What prompt engineering controls

  • Task framing — tell the model exactly what to produce, for whom, and what not to do. Ambiguity in the ask is the #1 quality defect.
  • Constraints & output format — JSON schemas, "answer with the SQL only," length caps. Constraining the output surface kills whole failure modes.
  • Few-shot examples — two or three well-chosen examples teach format and tone better than a paragraph of instructions.
  • Role / persona & rubric — "you are a security reviewer" + explicit success criteria align the model with the bar you'll grade against.
  • Decomposition — breaking a task into steps (or asking for step-by-step reasoning) squeezes more out of a single turn before you need an agent.

8.2 Where it hits its ceiling

Prompt engineering only governs the words you send — not the information around them (that's context engineering) nor what happens after the first response (that's loop engineering). The moment a task needs retrieved documents, tool outputs, or multi-step autonomy, tuning the prompt alone plateaus. As Anthropic frames it, the question shifted from "what phrasing works?" to "what configuration of context produces the desired behavior?"

When it's still the right tool: human-reviewed single-turn work — rewrite a paragraph, summarize a transcript, translate, explain an error — and prototyping. If a clean prompt with good examples fails, that's the signal to add context or a loop, not more adjectives.

08 Context Engineering — the window is a budget

The second step of the evolution. When single-turn prompting gave way to multi-turn agents, the optimizable surface expanded from the prompt to everything the model sees on a call — system instructions, tool schemas, retrieved documents, message history, memory. Context engineering is curating that set of tokens and deciding what stays out. The model has no memory between requests; everything it "knows" in a turn is what the harness assembled. Context is a budget with three costs: money (input tokens), latency (prefill), and quality (diluted attention).

9.1 Window vs length — and why pricing cliffs matter

The context window is the model's hard capacity (1M tokens on Claude 5, GPT-5.6, Gemini, Kimi K3). Context length is how much you actually sent on a request. Pricing tiers and KV-cache behavior depend on length: Gemini 3.7 Flash doubles input price above 200K; GPT-5.6 charges 2× input / 1.5× output above ~272K. An agent that lets history grow unpruned crosses those cliffs silently.

9.2 Prompt caching — the mechanics behind the 90% discount

Caching is a prefix match: the provider pins the KV cache (the already-computed key/value vectors) of your prefix in GPU memory. On a cache hit, the expensive prefill step is skipped for the prefix — only the new suffix gets processed. That's why the discount is real (~90% at Anthropic, 10× at Kimi/DeepSeek) and why TTLs exist (5 min / 1 h at Anthropic): VRAM is expensive and caches get evicted.

  • Any changed byte in the prefix invalidates everything after it. A timestamp in the system prompt, JSON serialized without stable ordering, a tool added mid-session — each one zeroes the cache.
  • Stable first, volatile last. Frozen system prompt and deterministic tool list up front; per-turn content (user question, timestamps) after the last cache breakpoint.
  • Cache writes cost a premium (~1.25× at Anthropic for the 5-min TTL); reads cost ~0.1×. Break-even arrives on the second hit — but only if the prefix actually repeats.
  • Verify with the usage fields (cache_read_input_tokens etc.). If cache reads are zero across repeated requests, a silent invalidator is at work — diff the rendered prompt bytes.

9.3 Compaction, pruning, and context rot

Models degrade well before the window fills — the "lost in the middle" effect: information buried mid-way through a huge context gets less attention than the start and end. Long agent sessions also accumulate garbage: stale tool results, failed attempts, obsolete reasoning. That's context rot. The defenses:

  • Compaction — as the session nears the limit, older turns get summarized into one compact block and the conversation continues. Providers now offer this server-side; harnesses (Claude Code, Cursor) have done it client-side for years.
  • Tool-result pruning — old tool outputs rarely matter after they've been consumed. Clear them or replace with a one-line summary. (The classic 350KB-JSON mistake from §05 starts here.)
  • Externalize state — memory (§06), note files, RAG. What doesn't need to be in context should be retrievable.
  • Subagents as context isolation — delegate a subtask with a clean context and get back only the conclusion, not the 40 tool calls that produced it.
Killer line: "Context isn't a scratchpad, it's a budget. Every token in the prompt competes for the model's attention and for your money. Context engineering is deciding what stays out."

09 Loop Engineering — driving the agent to done

The newest layer, which emerged once models and context got good enough that the bottleneck moved to what happens across many turns. Loop engineering is designing the agentic loop that iteratively drives an agent toward a goal with minimal human intervention — the observe → act → verify → adjust cycle, plus the budgets and stop conditions that keep it honest. Where prompt engineering shapes one instruction and context engineering shapes one turn's information, loop engineering shapes the workflow that keeps running after the first model call.

10.1 The core loop

Four stages that repeat until a verifiable stop condition is met: Goal (the success criterion, re-checked each pass) → Action (the agent takes a step, usually a tool call) → Observation (the system evaluates the result — CI tests, a verifier, a diff) → Adjustment (feedback refines the next action). It's the same state machine as the harness loop (§05), now treated as something you deliberately design rather than an improvised while.

10.2 What you actually engineer

  • Verification / self-correction — a separate verifier subagent (with its own instructions) checks the artifact against explicit criteria: tests pass, rubric met, the real flow driven end-to-end as a human would — not the agent's own confidence. This is the defect Anthropic calls "marking work done without actually testing it."
  • Retries that learn — bounded retries that feed the failure back so the next attempt differs, rather than repeating the identical call.
  • Budgets — hard caps on tokens, wall-clock, and iterations so a stuck agent can't burn $50 overnight (the "unbounded loops" pitfall from §05).
  • Stop conditions — "done" defined by measurable artifacts (a feature checklist, green CI), not vibes. Without them the loop stops too early or never.
  • State bridging / checkpointing — progress files, git history, and notes so work survives context resets across long sessions (ties to memory §06 and compaction §08).
  • Subagent orchestration — specialized sub-loops (a testing agent, a QA agent, a cleanup agent) with isolated context, each doing one sub-task better.
  • Human-in-the-loop gates — approval before sensitive or irreversible actions. Automation doesn't remove human judgment; it positions it at the right points.
  • Event-driven triggers — webhooks, cron, message queues turn a one-shot agent into a system that runs continuously in the background.
Killer line: "Prompt engineering shapes the instruction. Context engineering shapes what the model sees. Loop engineering shapes what happens next — and it's where reliability lives once the model and the context are already good. The three stack; none replaces the last."

10 Custom MCP — Model Context Protocol

MCP is the "USB-C for AI" — a standardized protocol (Anthropic, late 2024, now broadly adopted) for letting any LLM client talk to any tool/data source.

If you already know REST APIs, here is the analogy

A REST API exposes resources at URLs (GET /users/42) so that humans writing code can integrate with your system. Each client (web app, mobile app, partner backend) writes its own integration: pick endpoints, parse responses, handle auth, retry on failures.

An MCP server exposes tools, resources and prompts over a standard protocol so that any LLM client can integrate with your system without writing client code. The LLM discovers what is available, reads the schemas, and decides at runtime which tool to call.

Same idea — "expose capabilities so something else can call them" — but the caller is an LLM agent, the discovery is automatic, and the contract is uniform across every AI tool in your stack (Claude Desktop, Claude Code, Cursor, Windsurf, Codex, etc).

Mental model: REST is "an API for code." MCP is "an API for LLMs." You can absolutely wrap an existing REST API in an MCP server — and that is exactly what most production MCPs do (the Jira MCP, GitHub MCP, Linear MCP are all thin wrappers over their respective REST/GraphQL APIs, repackaged with LLM-friendly descriptions and schemas).

What MCP adds that REST does not

  • Self-describing tools. The LLM asks "what can you do?" and gets back tool names, descriptions, and argument schemas it can validate against. No human reads OpenAPI first.
  • One integration → every AI client. Build the Jira MCP once; Claude Desktop, Claude Code, Cursor, Codex, Windsurf all use it.
  • Resources are LLM-aware. A resource is a "thing the LLM can pull into context" — not just "data returned from a call." The protocol distinguishes that.
  • Prompts as a first-class primitive. The server can ship reusable prompt templates (e.g. /review-pr) — REST has no analog.
  • Session and notifications. Server can push updates (e.g. "this resource changed, refresh"). REST needs WebSockets or polling for that.

Three primitives an MCP server can expose

  • Tools — functions the LLM can call (write actions, queries).
  • Resources — file-like read-only data the client can fetch.
  • Prompts — pre-written templates users can invoke.

Transport

  • stdio — local subprocess. Used for desktop apps (Claude Desktop, Cursor, Claude Code locally).
  • Streamable HTTP — remote, scalable. For cloud-deployed servers, multi-tenant. It replaced the older standalone HTTP+SSE transport; SSE may still appear inside Streamable HTTP for server-to-client streaming.
  • Wire format: JSON-RPC 2.0 over either transport.

Minimal TypeScript MCP server (sketch)

import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";

);

SDKs available

  • Python — mcp (official). Most popular.
  • TypeScript — @modelcontextprotocol/sdk.
  • C# — official Microsoft SDK (good news for you given your background).
  • Java, Go, Rust — community.

When to build one

  • You have an internal system (Jira, internal DB, monorepo CLI) that you want every AI tool (Claude Code, Cursor, Codex) to access uniformly.
  • You want auth, rate-limiting, audit-logging on tool calls in one place.
  • Compare to: plain function-calling — works, but every client needs its own integration.

11 DAG — Directed Acyclic Graph

A graph of nodes + directed edges with no cycles. In AI agent land, nodes are LLM calls / tools / retrievers / branches; edges are dependencies. No cycles = execution always terminates.

Why DAGs for agents

  • Explicit data flow — easy to reason about, log, replay.
  • Parallel execution where edges allow.
  • Deterministic scheduling, retries per node, partial failure recovery.
  • Easy observability — every node is a checkpoint.

Frameworks

  • LangGraph — DAG-based agent orchestration in the LangChain ecosystem. State + nodes + edges. The reference.
  • LlamaIndex Workflows — similar pattern, event-driven.
  • Haystack (deepset) — pipeline DAGs.
  • Inngest / Temporal / Prefect / Airflow — general-purpose DAG schedulers being adopted for AI.

2026 nuance

Pure DAGs are restrictive — real agents often want conditional cycles (re-plan, retry). LangGraph supports cycles but encourages bounding them with iteration limits. The pattern is "DAG with controlled loops" rather than free-form recurrence.

Adaptive multi-agent systems can now restructure their DAGs at runtime based on intermediate results — this is a hot research area.

12 RAG — Retrieval Augmented Generation

"Pre-pend relevant context to the prompt." The naive version fails 40% of the time at retrieval — the 2026 stack is hybrid + reranked + sometimes graph.

The modern stack

  1. Chunking — semantic / sliding-window chunks (300–800 tokens). Track parent doc.
  2. Embedding — dense vectors (OpenAI text-embedding-3-large, Cohere, BGE, Voyage).
  3. Hybrid retrieval — BM25 keyword + vector similarity in parallel, fused with Reciprocal Rank Fusion (RRF). The single biggest quality win over naive.
  4. Reranking — top-50 → cross-encoder reranker (Cohere Rerank, BGE-reranker) → top-5. Highest-ROI step. +25–40% precision.
  5. Generation — pass top-K + query to LLM. Cite sources.
  6. Eval — RAGAS metrics (faithfulness, context precision, answer relevance).

When RAG vs alternatives

  • RAG — knowledge changes often, large corpus, need citations.
  • Long context (Gemini 1M, etc.) — small enough corpus to fit; cost permits.
  • Fine-tuning — style/format, not facts. Don't use fine-tuning for fresh data.
  • GraphRAG — multi-hop questions over a structured domain.
Bumper sticker: "In 2026, retrieval is the bottleneck, not generation. Hybrid + rerank is the default." Don't reach for fancier (HyDE, multi-query, agentic RAG) until you've measured RAGAS scores and proved you need it.

13 LLM-wiki & Open Knowledge Format

An LLM-wiki is a persistent, plain-text knowledge base that an agent maintains for other agents and humans. The Open Knowledge Format (OKF) turns that informal pattern into a portable, vendor-neutral format: a tree of Markdown files with YAML metadata and ordinary links between concepts.

The problem it solves

Operational knowledge is usually scattered across schemas, runbooks, tickets, code, and tribal memory. Putting all of it into one giant prompt is expensive and goes stale; locking that context into a proprietary database or SDK makes it hard to reuse. An OKF bundle keeps knowledge human-readable, Git-versionable, and consumable by different agents without vendor-specific translation.

Minimal OKF v0.1 bundle

knowledge/
├── index.md
├── log.md
├── metrics/
│   └── monthly-active-users.md
└── systems/
    └── billing-api.md

---
type: metric
title: Monthly active users
owners: [growth-data]
status: active
---

# Monthly active users
Calculated from authenticated product events.
See [Billing API](../systems/billing-api.md).

Important rules and fields

  • Each concept document is a UTF-8 .md file and needs YAML frontmatter with a non-empty type. The schema is open: fields such as title, owners, status, and tags may be added for the domain.
  • index.md guides navigation and log.md records changes. Those names are reserved and do not count as concept documents.
  • Ordinary Markdown links form a portable knowledge graph. The file path acts as the concept's stable identity.
  • The format requires no vector database, central registry, SDK, or runtime. Validation, search, and updates belong to the tools that produce and consume the bundle.

How it fits into the stack

  • RAG: OKF organizes the corpus; RAG selects which pages or passages enter context. OKF does not replace retrieval.
  • GraphRAG: explicit links and types provide a natural base for traversal and multi-hop retrieval.
  • MCP: an MCP server can expose OKF bundle search, reading, and updates to any compatible harness.
  • Evals: measure coverage, freshness, broken links, retrieval precision, and answer faithfulness to the bundle.
Mental model: LLM-wiki is the working pattern — agents compile and maintain living knowledge. OKF is the file contract that lets that knowledge move between tools. See the Google Cloud introduction and the v0.1 spec.

14 Grafo de Pesquisa (Research Graph)

"Research graph" shows up in two related contexts — make sure you can distinguish them.

1. Deep Research agents (the "research graph" as workflow)

An agent that iteratively plans → searches → reads → synthesizes, building a graph of sub-questions where each node is a search query/document and edges encode "this finding led to that follow-up." Google's Deep Research, OpenAI Deep Research, and Anthropic's Research feature all follow this pattern.

  • Long-running (minutes, not seconds).
  • Uses test-time compute — many model calls to refine.
  • Connects to web + MCPs + uploaded files.
  • Output is typically a long structured report with citations.

2. GraphRAG (the "research graph" as data structure)

Instead of retrieving flat chunks, you build a knowledge graph from your corpus (entities + relationships) and retrieve connected subgraphs at query time. Better for multi-hop questions ("which authors collaborated with X on topic Y between 2020-2024?") that flat RAG fails on.

  • Microsoft GraphRAG popularized this in 2024 — by 2026 production-grade.
  • Deep GraphRAG, FastInsight are current research frontier — hierarchical retrieval, semantic-topological reranking.
  • Vector RAG retrieves semantically similar facts; graph RAG retrieves relationally connected facts.
If asked "what's a research graph": Lead with the agent workflow (search graph as a thinking trace), then mention GraphRAG as the data-side counterpart. Bonus: mention that in both cases the graph is a DAG at execution time (no cycles, dependencies flow forward).

15 Evals vs Benchmarks — and how to build each

PurposeCompare models in isolationMeasure your app at a specific job
DatasetPublic, standardized (MMLU, SWE-bench, GPQA, HumanEval, AIME)Custom, drawn from your domain + production failures

StabilityFrozen — saturates over timeLiving — grows with each prod regression

How to build an eval suite (production pattern)

  1. Define the task + success criteria. Not "be helpful" — "extract the order ID from emails with ≥98% accuracy."
  2. Seed dataset from real production traces. Hand-label 50–200 examples covering golden path + edge cases.
  3. Pick a grader:
    • Exact match / regex (cheapest, brittlest)
    • Code-based (assertions, JSON schema)
    • LLM-as-judge (flexible, biased — pair with rubric + calibration)
    • Human review (gold but slow)
  4. Run in CI on every prompt/model change. Block merges on regressions.
  5. Auto-grow from failures: every production incident becomes a new test case — the regression suite is your moat.
  6. Layer it: automated evals pre-launch → A/B test in prod → user feedback loop → distribution drift monitoring.

How to build a benchmark (rarely what you want)

  1. Define a capability, not a product — "reasoning over chains of arithmetic" not "our checkout bot."
  2. Collect public, hold-out dataset. Document contamination policy (was the model trained on it?).
  3. Single objective metric. Reproducible scripts. Versioned.
  4. Publish — it only matters if others run it.

Key tools (2026)

  • OpenAI Evals, DeepEval, Promptfoo, Braintrust, LangSmith, Inspect (UK AISI).
  • RAGAS for RAG-specific metrics (faithfulness, context precision, answer relevance).
The killer line: "Benchmarks tell you which model to start with. Evals tell you when you're shipping a regression." If you only remember one thing about this section, remember that.

17 Spec-Driven Development (SDD)

"Inversion of the power structure: specifications no longer serve code — code serves specifications." Specs become executable artifacts that gate AI codegen.

The four (sometimes five) phases

  1. Constitution — persistent project principles: tech stack, coding standards, security rules. Immutable context for every AI run.
  2. Specification — unambiguous user stories, acceptance criteria, constraints. Intent only — no implementation.
  3. (Clarification) — structured pass to surface unspecified edge cases. Q&A logged back into the spec.
  4. Architecture / Plan — human-in-the-loop technical plan. Tech choices, module boundaries, data model. You review and sign off.
  5. Tasks — break the plan into discrete, AI-executable tasks. Modeled as a DAG (Task Graph): dependencies explicit, parallelism where possible.
  6. Implementation — AI agent walks the task DAG, generates code, runs tests, marks tasks complete.

Why the Task Graph is a DAG

  • Tasks have dependencies (B needs A's schema, C and D can run in parallel).
  • No cycles means the agent can schedule work — execute leaves first, work up.
  • Failure isolates to a subtree. You can re-run one task without losing the others.
  • This is exactly how build systems (Bazel, Nx) have always worked — SDD borrows the pattern.

Tools (2026)

  • GitHub Spec Kit — open-source toolkit, the reference implementation. Has /specify, /plan, /tasks commands.
  • Kiro (AWS) — GA Nov 2025. VS Code fork with deep SDD integration.
  • Tessl — spec-as-the-source-of-truth approach.
  • Claude Code, Cursor — increasingly bake in spec-driven workflows.
The essential framing: "Traditional specs are documents humans read. SDD specs are contracts the AI executes against — they gate codegen, drive task graphs, and survive across model versions. The spec is the durable artifact; the code is a refreshable build product."

Where it intersects everything else in this guide

  • The Task Graph is a DAG (§11).
  • Each task often runs through a research graph (§14) — read related code, find prior patterns.
  • Evals (§15) become the executable acceptance criteria.
  • Prompts driving each phase are versioned (§16).
  • The agent uses MCP (§10) to talk to git, the build, the test runner.
  • Context7 (§19) feeds it the actual library APIs to use.

19 What is Context7?

Context7 is an MCP server (built by Upstash) that serves up-to-date, version-specific library documentation into your AI coding tools — Cursor, Claude Code, Windsurf, OpenCode, anything that speaks MCP.

The problem it solves

LLMs hallucinate APIs because their training cutoff lags real library releases. Context7 fetches fresh docs at query time so the model sees the actual current API rather than reciting a 2-year-old version from memory.

How it works

  • Two tools exposed via MCP:
    • resolve-library-id — map "react query" to a Context7 ID.
    • query-docs / get-library-docs — fetch version-specific docs by ID + query. The visible name depends on the client/package wrapper.
  • Free tier, MIT-licensed server, optional API key for higher rate limits.
  • Hosted at context7.com.

Why Upstash?

Upstash is a serverless-Redis / messaging company. They built Context7 as a developer-tool play and run it on their own infra — that's why they can offer a free tier sustainably.

Use case: Any time you ask Claude/Cursor to use a library and it generates calls to a function that doesn't exist or moved — that's Context7's pitch. Add "use context7" in your prompt and the tool will pull current docs.
